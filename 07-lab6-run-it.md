## Framing (2 min)

Say what Aspire is here, because the word carries baggage:

- It is a local orchestrator plus a dashboard. One command starts every resource the
  application needs, wires the connection strings between them, and collects the telemetry.
- It is NOT a framework you build against. Nothing in Domain, Application, Infrastructure or
  Presentation changes in this block. The only code edit outside two new projects is about ten
  lines in the composition root.
- The same graph is the deployment description. What you declare in `AppHost.cs` is what gets
  provisioned, which is why the last beat of the block is a deploy and not a separate lab.

**File: `src/Helpdesk.AppHost/AppHost.cs` (new file)**

```csharp
var builder = DistributedApplication.CreateBuilder(args);

// Aspire runs its own SQL Server container. It gets its own container name and whatever host
// port Aspire assigns, so the docker compose container on 14330 that labs 1 to 5 use keeps
// running beside it and neither one can take the other's port.
var sql = builder.AddSqlServer("sql")
    .WithContainerName("helpdesk-aspire-sql")
    .WithLifetime(ContainerLifetime.Persistent)   // survives a stop, so a restart is seconds
    .WithDataVolume("helpdesk-aspire-sql-data");  // and the data survives with it

// The resource name is the connection string name that WithReference injects. Calling this
// database "Tickets" is what lands it on ConnectionStrings:Tickets, which is the key the
// Tickets module already reads. The physical database is still HelpdeskTickets.
var tickets = sql.AddDatabase("Tickets", "HelpdeskTickets");

builder.AddProject<Projects.Helpdesk_Host>("api")
    .WithReference(tickets)

    // WaitFor gates startup on the SQL resource reporting healthy: that is liveness of a
    // dependency, and it is the right thing to wait on. A service must never gate its own
    // startup on its own readiness endpoint (/health), because /health only goes green after
    // the schema is in place, and the schema only arrives after the service starts. Wait on
    // what you depend on, report your own readiness, and never wait on yourself.
    .WaitFor(tickets)

    // Only the orchestrated run migrates on startup. Labs 1 to 5 keep using
    // dotnet ef database update against the compose container, so the default stays off.
    .WithEnvironment("Migrations__ApplyOnStartup", "true");

builder.Build().Run();
```

Three things to say out loud while it is on screen, in this order:

1. **The resource name IS the connection string name.** `AddDatabase("Tickets", ...)` is what
   makes `WithReference` inject `ConnectionStrings__Tickets`, the key the Tickets module has
   been reading since Lab 3. Nothing in the module changed: that is why the AppHost is
   additive rather than invasive.
2. **No host port.** Aspire's SQL container is deliberately not mapped to 14330, so the
   compose container from the morning keeps that port and keeps running and nobody's Lab 3
   migration breaks at 2:20. Two SQL Servers on one laptop is fine; two fighting for one port
   is not.
3. **Migrate-on-startup is an explicit switch, not an environment sniff.** Labs 1 to 5 keep
   `dotnet ef database update`; only the AppHost sets `Migrations__ApplyOnStartup=true`, and
   the API tests, which drop and re-create their own database, never see it. An explicit
   setting reads in one line; `if (env.IsDevelopment())` reads as a guess.

```csharp
    public static WebApplication MapDefaultEndpoints(this WebApplication app)
    {
        // The template maps these in Development only. We map them in every environment
        // because a container probe reads them from outside the app, where the environment
        // name is whatever the platform set. Both endpoints are unauthenticated, so do not
        // put secrets in a check description.

        // Readiness: every check, including the database. "Can this instance take traffic?"
        app.MapHealthChecks(HealthEndpointPath);

        // Liveness: only checks tagged "live". "Is this process worth keeping alive?"
        app.MapHealthChecks(AlivenessEndpointPath, new HealthCheckOptions
        {
            Predicate = registration => registration.Tags.Contains("live"),
        });

        return app;
    }
```

using Helpdesk.Tickets.Presentation;
using Microsoft.EntityFrameworkCore;

var builder = WebApplication.CreateBuilder(args);

// Telemetry, resilience, service discovery and the "self" liveness check.
builder.AddServiceDefaults();

builder.Services.AddTicketsModule(builder.Configuration);

// Readiness only: this check is untagged, so /health waits on the database and /alive does not.
builder.Services.AddHealthChecks()

app.MapDefaultEndpoints();

// switch beats sniffing the environment: you can read it in one line, the labs that run the

// which drop and re-create their own database in the factory, never migrate twice.
if (app.Configuration.GetValue<bool>("Migrations:ApplyOnStartup"))
{
    using var scope = app.Services.CreateScope();
    await scope.ServiceProvider.GetRequiredService<TicketsDbContext>().Database.MigrateAsync();

app.Run();

## Liveness vs readiness (2 min)

### Step 3: the two health endpoints, and the rule

Two curls, then the rule:

```sh
curl -i http://localhost:5000/alive
curl -i http://localhost:5000/health
```

Three facts, in order:

- `/alive` only runs checks tagged `live`, and the only such check is `self`, which returns
  healthy and checks nothing else on purpose. "Is this process worth keeping alive?"
- `/health` runs everything, including `AddDbContextCheck<TicketsDbContext>`. "Can this
  instance take traffic right now?" A database outage turns this red and leaves `/alive`
  green, which is exactly right: restarting the process would not help.
- Both are mapped in **every** environment, not just Development. A container probe reads them
  from outside the process, where the environment name is whatever the platform happened to
  set. The template's Development-only mapping is the bug that ships as a crash loop.

Then the rule, and put it on a slide because it is the one sentence from this block people will
repeat: **startup gates on liveness, never on readiness.** `WaitFor(tickets)` holds the API
until SQL reports healthy, which is a dependency's liveness and is the right thing to wait on.
Nothing waits on the API's own `/health`, because readiness only goes green after the schema is
in place and the schema only arrives after the API starts. Wait on what you depend on, report
your own readiness, never wait on yourself. Teams deadlock their own deployments with this
roughly once.

## If things go wrong

- **macOS: the `api` resource fails with `address already in use` on 5000, or the curls get
  `403 Forbidden` from `AirTunes`.** AirPlay Receiver owns port 5000 on a Mac. Switch it off
  (System Settings > General > AirDrop & Handoff > AirPlay Receiver) and run the AppHost again.
- **Apple Silicon: the `sql` resource keeps restarting or exits.** Docker Desktop's Rosetta
  setting is off and the amd64-only SQL Server image cannot run. Settings > General > "Use
  Rosetta for x86_64/amd64 emulation on Apple Silicon", restart Docker, run the AppHost again.
- **Aspire CLI too old.** `Unrecognized command or argument 'agent'` means a pre-13.2 CLI.
  Update the CLI; there is no manual substitute for the MCP half, which is why the clinic
  checks it and the projector machine gets updated before the day.
- **Docker not running.** The AppHost cannot start SQL and `api` never leaves Waiting. Start
  Docker Desktop and re-run; the persistent container lifetime makes the second start seconds.
- **`sql` and `Tickets` stuck at Running (Unhealthy), `api` stuck at Waiting.**
  `docker logs --tail 5 helpdesk-aspire-sql` repeats `Login failed for
  user 'sa'. Reason: Password did not match`. The SQL data volume survived from an earlier run
  (anyone who rehearsed Lab 6 at home, then rebuilt or recloned the AppHost): the new AppHost
  generated a new `sa` password into its user secrets, but SQL Server only applies
  `MSSQL_SA_PASSWORD` when it first creates `master`, so the old volume still holds the old
  one. Fix: Ctrl+C the AppHost (the persistent container keeps running), then the handout's
  Troubleshooting block. Its first line prints the volume name (`helpdesk-aspire-sql-data` with
  the handout code; `helpdesk.apphost-<hash>-sql-data` if the AI path wrote an unnamed
  `.WithDataVolume()`, so swap that name into the last line):

  ```sh
  docker inspect helpdesk-aspire-sql --format "{{range .Mounts}}{{.Name}}{{end}}"
  docker rm -f helpdesk-aspire-sql
  docker volume rm helpdesk-aspire-sql-data
  ```

  Then start the AppHost again. Only rehearsal tickets are lost; `Migrations__ApplyOnStartup`
  rebuilds the schema.
- **An attendee mapped host port 14330 in their AppHost.** By design nothing here binds a host
  port, so there is no clash. If somebody added one to "make it reachable": the compose
  container owns 14330, whichever container starts second fails or silently shadows the other,
  and their morning connection strings break. Remove it; read the port off the dashboard.
- **No dashboard URL.** `aspire run` printed it with the login token in the query string;
  scroll the terminal up. Typing the host name by hand lands on a login page with no token.
- **The agent cannot see the Aspire MCP server.** In order: is `.mcp.json` at the repository
  root, was the agent restarted after it appeared, does `/mcp` list `aspire` as connected. If
  it is listed but failing, run `aspire agent mcp` in a terminal and read the error (if it
  starts cleanly it just waits on input; Ctrl+C to stop).
- **The app runs, but `aspire ps` says "No running AppHost found" and `list_apphosts` is
  empty.** The AppHost is still on `Aspire.AppHost.Sdk/13.0.0`. Bump the `Sdk` line and
  `Aspire.Hosting.SqlServer` to `13.6.0`, add `<AspireUseCliBundle>true</AspireUseCliBundle>`,
  restart the run. The CLI prints no warning; it simply cannot see the older AppHost.
- **Migration did not apply, endpoints 500 on a missing table.** Check the `api` resource's
  environment in the dashboard for `Migrations__ApplyOnStartup`. Note the double underscore:
  the key is `Migrations:ApplyOnStartup`, and a single underscore silently does nothing.
- **The agent fixes it by reading the code instead of the telemetry.** Still a correct fix,
  still a worse demo. Undo, re-ask with "do not open any source file until you have read the
  error log through the aspire MCP server", and say out loud why you are insisting.
- **Behind schedule.** Cut the deploy to one spoken sentence first. Then compress the dashboard
  beat to the trace only, skipping structured logs, since the closed loop re-teaches them. The
  closed loop is never cut; without it this block is a tooling demo.
