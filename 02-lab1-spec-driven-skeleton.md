## Step 1: repo + context file FIRST (together, on screen)

Narrate the inversion: "Everyone's instinct is to prompt first and explain later. We write the
explanation first, because the context file is the difference between an agent that guesses
and an agent that follows your rules."

Before anyone types, say the terminal rule (handout Step 1 prints it): on Windows, Git Bash for
every command today. Command Prompt fails on `rm`, on `<owner>` placeholders (read as a file
redirect) and on Lab 5's heredoc; PowerShell fails on the heredoc. A 2026-10-07 run in cmd.exe
hit all three. On a Mac, the stock Terminal (zsh) runs everything, after one line:
`setopt interactivecomments` (the handout has the `~/.zshrc` form). Without it zsh hands the
trailing `# comment` words to the command: the very next block's
`docker compose up -d   # SQL Server 2022; ...` dies with `no such service: #`, and later
`dotnet build Helpdesk.slnx # green ...` with `MSB1008`. Also on a Mac: AirPlay Receiver owns
port 5000, the API's port from Lab 3 on; ask Mac users to switch it off now (the check script
flags it). Ctrl+C stops a running host on both OSes (Control, not Command, on a Mac).

Then the editor rule, same breath (handout Step 1 prints it too): on Windows, paste file
contents into VS Code, not Notepad. Notepad's Markdown formatting escapes the paste (`\#`,
`\-`, `\---`, `&#x20;` for indents) and saves the escapes. The 2026-10-08 rehearsal pasted
CLAUDE.md, the spec and the slice skill through Notepad: the headings broke and the skill's
frontmatter became `\---`, so Lab 3's `/slice` loses its name and description. A file whose first line starts with
a backslash is this, not a code bug.

**File: `CLAUDE.md` (new file)**

```markdown
# Helpdesk

Modular monolith on .NET 10. Modules live under src/Modules/<Name> with four projects:
Domain, Application, Infrastructure, Presentation. Composition root is Helpdesk.Host.

## Commands
- Build: dotnet build Helpdesk.slnx
- Test: dotnet test Helpdesk.slnx
- Run: dotnet run --project src/Helpdesk.Host

## Layer rules (enforced by tests in Helpdesk.ArchitectureTests)
- Domain references only Helpdesk.SharedKernel. No NuGet packages in Domain.
- Application references Domain. Infrastructure and Presentation reference Application.
- Only Host references Infrastructure. Modules never reference other modules' internals.

## Conventions
- Errors: return Result / Result<T> from SharedKernel. Never throw for business rule
  failures. Exceptions are for bugs and infrastructure faults only.
- Entities: private constructors, static factory methods returning Result<T>.
- Handlers: one command or query per file, handler beside it, internal visibility.
- Nullable enabled, warnings as errors, file-scoped namespaces.
- Never: add a NuGet package without asking; touch the database schema without a migration.

## Git
- Stay on the checked-out branch (main, unless the developer switched it). Do not create,
  switch, merge or delete branches.
- Do not commit or push. The developer commits after dotnet build and dotnet test pass.
- These Git rules win over any branch or pull-request workflow in a CLAUDE.md or AGENTS.md
  from a parent folder or from user settings.
```

## Step 2: the spec (solo, 3 min)

Name it out loud before they type: this is **spec-driven development**. The requirements and the
design go into a written spec first, the agent executes the spec, and the spec is what you
review when the output looks wrong. We are doing the lightweight version by hand, in one
Markdown file, because the practice is the point and the practice fits on one page.

Slide cue (one slide, 30 seconds): **GitHub Spec Kit** and **AWS Kiro** are the tooling that
formalises this - templates, a constitution file, generated plans and task lists. Say that they
are worth a look after today, that the loop they automate is exactly the one we are about to run
by hand, and move on. Do not demo either one; the room has fifty minutes and no time for a
second tool install.

Attendees write `docs/lab1-spec.md` in their repo (handout has it verbatim):

**File: `docs/lab1-spec.md` (new file)**

```markdown
Create the solution skeleton described in CLAUDE.md:
- Helpdesk.slnx at the root. Projects: src/Helpdesk.SharedKernel, src/Helpdesk.Host,
  src/Modules/Tickets/Helpdesk.Tickets.{Domain,Application,Infrastructure,Presentation},
  tests/Helpdesk.Tickets.Domain.Tests, tests/Helpdesk.ArchitectureTests.
- SharedKernel, Domain, Application: classlib. Infrastructure: classlib with
  Microsoft.EntityFrameworkCore.SqlServer. Presentation: classlib with a
  Microsoft.AspNetCore.App framework reference. Host: web project.
```

## Step 3, AI path: plan-mode scaffold (solo, ~17 min)

What attendees do (handout lab1, "Step 3, AI path", word for word):

Run `claude --permission-mode default` (new installs otherwise start in auto mode, and today
you want to see every permission prompt; in VS Code, pick Manual in the mode indicator), press
**Shift+Tab** until you are in plan mode, then type:

> Read CLAUDE.md and docs/lab1-spec.md, then scaffold the solution exactly as specified.

**Read the plan before approving it.** Reject anything you did not ask for (extra packages,
Dockerfiles, CI files) and say why. The spec names every project path and every allowed
reference, so check the plan's project paths and references against the spec (and the Target
structure and Dependency rule at the top of this page); if they differ, say so and let it
revise. Approve with **Yes, manually approve edits** (NOT the first option, "Yes,
and use auto mode", which switches the session to auto mode and the prompts stop). Then watch
the permission prompts: each one is a chance to catch a step you did not intend.

When it finishes, it may offer to commit or to create a branch (for example `lab1-scaffold`).
Say no: Lab 1 stays on `main`, and the commit is yours, in Step 4,
after the build and tests pass.

What the agent should produce: the eight projects and references of the Target structure, the
Program.cs `/health` stub, and the placeholder files shown under "End state of Step 3" below
(rehearsed 2026-10-06: plan 24 s, apply 72 s, no invented packages, Dockerfiles or CI files).

Coach from the front while they work:

- **Read the plan before approving.** Look for invented extras (a Dockerfile you did not ask
  for, an extra package). Reject and say why; the revision is the lesson.
- **Check the layout against the spec.** The spec names every project path and every allowed
  reference, because CLAUDE.md names the four layers, not the folders: it never mentions
  `tests/`, the test project names, or Host -> Presentation. An earlier spec left those out and
  the agent filled them in by guessing (a rehearsal plan said so: "the spec doesn't give folder
  or project names, so I picked them from CLAUDE.md"). Have attendees compare the plan's project
  paths and references with the spec, and send it back if they differ.
- If the plan has no extras, say that out loud: the spec was precise enough. The most common
  unrequested item is a "run the host and curl /health" verification step; harmless, but still a
  step you did not ask for.
- **When the plan dialog appears, say it out loud: pick "Yes, manually approve edits".** The
  first option, "Yes, and use auto mode", switches the session to auto mode and the room sees no
  prompts for the rest of the lab.
- Permission prompts are a feature, not friction: each one is a chance to catch a step you did
  not intend.
- When the agent finishes, it should build. If it claims success, the next step verifies.
- If it offers to commit or to create a branch (a 2026-10-07 attendee run proposed
  `lab1-scaffold`), say no out loud: nothing in the brief asked for either, so it filled the gap
  with a plausible default. The commit is Step 4, after the build and tests pass.

## If things go wrong

- Mac, `no such service: #` from `docker compose up -d`, `MSB1008: Only one project can be
  specified` from `dotnet build`, or `zsh: command not found: nothing`: zsh is reading the
  trailing `# comment` as arguments (and the `;` inside it as a second command). Fix:
  `echo 'setopt interactivecomments' >> ~/.zshrc`, new terminal window, rerun the block.
- Apple Silicon, the SQL container exits seconds after `docker compose up -d` (`docker ps`
  shows nothing, `docker compose logs sql` ends abruptly): Docker Desktop's Rosetta setting is
  off and the amd64-only SQL image cannot run under the fallback emulator. Settings > General >
  "Use Rosetta for x86_64/amd64 emulation on Apple Silicon", restart Docker, rerun. Not
  blocking until Lab 3.
- Agent scaffolds a wrong layout: do not debug live; have them checkout `lab1-end` and move
  on. Debug one attendee's transcript during the break as a group learning moment if useful.
- Docker/SQL failures do NOT block this lab (nothing touches the database yet); park them for
  the break and say so out loud, since stragglers will be anxious about it.
- Room-wide wifi collapse: switch everyone to the manual path; the NuGet cache stick covers
  restore.
